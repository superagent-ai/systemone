# Organization-key authentication rollout — 2026-09-28

## Production change

Operator approved permission tightening, secret provisioning, and deployment. Modal
`systemone-api` version **v5**, tag `org-key-auth-20260928`, was deployed at
**2026-09-28 07:43:31 UTC**. The existing model, B200 GPU, one warm container, static
key secrets, and landing-to-Modal rewrite were preserved. The API is healthy.
Deployment history records source base `a6acdb3` with local implementation changes;
the implementation remains in the SystemOne checkout, not a published code PR.

The Supabase migration `20260928073841_systemone_key_lookup_rpc_and_helper_permissions`
is applied. Its SQL is recorded in [customer_auth.sql](../deployment/customer_auth.sql).
Verified: helper PUBLIC execution revoked, explicit app grants preserved, lookup RPC
denied to anon/authenticated and allowed to service_role, SECURITY INVOKER with empty
search_path, unknown hash returns no rows, and indexed lookup using `idx_api_keys_key_hash`.

The new server-only `systemone-customer-auth` Modal Secret contains
`SYSTEMONE_CUSTOMER_KEY_SUPABASE_URL` and `SYSTEMONE_CUSTOMER_KEY_SUPABASE_SERVICE_KEY`.
Static-key secrets were not changed; customer keys were not synchronized into secrets.
No authentication cache was added. Pool size is 8, total auth budget 1 second,
connect budget 1 second, and per-operation budget 0.5 second.

**Residual risk:** the service-role credential has broad project access and bypasses
RLS, including write capability. Only the RPC/query is read-only. The Supabase skill's
privilege audit found inherited HTTP-queue PUBLIC grants owned by Supabase internals
that project postgres cannot revoke. No direct-login lookup role was provisioned;
the permitted server-only service-role fallback was used instead. The API never
returns/logs this credential, and the inference subprocess does not inherit it.
See [AUTHENTICATION.md](AUTHENTICATION.md) for the scoped-role follow-up and setup details.

## Latency measurements

These are warm, fixed-small-payload measurements from a Modal CPU client, not broad
production traffic or large-prompt throughput tests. Inference concurrency is 4;
lookup-only concurrency is 8. Warmups are excluded. The model's inference/prefix
cache is unchanged; **authentication is always uncached**.

The first attempt failed during latency measurement; its test key was removed.
The second attempt retained all measurements and had **1 transport failure / 350
measured attempts** (direct inference: 99/100 HTTP 200; all other runs HTTP 200).
The underlying transport exception was not classified in that version of the tool.
The client read timeout was 130 seconds, so p95 alone does not describe the failure
tail. No HTTP 401 or 503 occurred in those measured attempts. This is not evidence
of an authentication/database outage; its underlying cause is not established.

Server timing sample counts exclude failed requests (99 for the direct inference
run); end-to-end percentiles include every measured attempt. Percentiles use
nearest rank. The static run is a sequential baseline, not a controlled estimate
of exact added latency: inference timings also varied between runs. Cold model/

sanitized representative payloads; see the benchmark commands in AUTHENTICATION.md.
No caching is proposed in this rollout. Any future positive cache would add a
revocation delay of up to its TTL, plus already authenticated in-flight requests.

The final run completed every security check and retained **1 failed attempt / 350**:

There were no transport errors in this run; both customer inference runs and the
static baseline were entirely HTTP 200. The verifier intentionally exits nonzero
when any benchmark attempt fails, even when all authentication/revocation checks pass.
This is not a zero-error production SLA or a clean load-test sign-off.

## Documentation and rollback

Docs PR: https://github.com/superagent-ai/app/pull/680. Both `content/docs/models-api.md`
and `public/llms.txt` remove the outdated claim that organization keys cannot work.
It is ready for review, not merged/published by this rollout. The hosted-support gate
is satisfied by successful live customer/static/deletion checks; the benchmark caveats
are separately recorded. There is no Next.js authentication hop.

Previous Modal version v4 remains available for rollback. Rolling back removes
organization-key support; do not delete the new secret to roll back this release,
as that makes the current version fail closed. The lookup RPC/helper permission
tightening does not require reversal for an API rollback. Never restore PUBLIC
helper execution without reviewing the security implications.
